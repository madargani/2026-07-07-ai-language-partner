    Create the full extraction pipeline implementation. Each file follows the patterns established in the codebase and documented in PATTERNS.md and RESEARCH.md.

    ### 1. src/prompts/extraction/system.md
    Create the extraction system prompt template (plain Markdown file, loaded at runtime). It instructs the LLM to analyze a language learner's message against their target language, distinguishing cognitive mistakes from mechanical typos (D-08), detecting code-switching (D-09/D-10), and following specific extraction rules. The prompt uses `{{targetLanguage}}` and `{{nativeLanguage}}` as template placeholders (replaced in the extraction service). Structure:
    - Role definition: extraction assistant for language learning app
    - User's target and native language context
    - Numbered rules (same pattern as `src/prompts/conversation/system.md`):
      1. Extract vocabulary items for new/unfamiliar words
      2. Extract grammar items for structural errors
      3. Mechanical typos → `typosIgnored`, do NOT create items (D-08)
      4. Cognitive mistakes → `detectedItems` with correct target-language term (D-08)
      5. Code-switching: native-language terms → infer target-language equivalent as `source` (D-09)
      6. Grammar items: `source` should describe pattern (e.g. "preterite vs imperfect")
      7. Do NOT create items for correctly used words
      8. Return empty `detectedItems` if nothing to extract
    - Format: brief, direct instruction — the output is constrained by the Zod schema

    ### 2. src/lib/queue.ts
    Create the BullMQ connection singleton + Queue + Worker + DLQ. Follow the pattern from PATTERNS.md §Pattern 1 and the RESEARCH.md code example:

    - Import `IORedis` from "ioredis" and `Queue, Worker` from "bullmq"
    - Import `env` from "../lib/config.js" (REDIS_URL env var)
    - Import `processExtractionJob` from "../services/extraction.js"
    - Create single `connection` ioredis instance with `maxRetriesPerRequest: null` (shared by Queue and Worker — Worker's internal `duplicate()` handles blocking internally)
    - Export `extractionQueue`: new Queue("extraction") with:
      - `connection`
      - `defaultJobOptions`: `attempts: 3`, `backoff: { type: "exponential", delay: 1000 }` (per D-05 — note: BullMQ exponential backoff uses seed delay, so attempts are ~1s, 2s, 4s; the exact 1s/5s/25s would need a custom backoffStrategy which is not needed for v1)
      - `removeOnComplete: { age: 3600 * 24 }` (keep completed 24h)
      - `removeOnFail: { age: 3600 * 24 * 7 }` (keep failed 7d)
    - Export `extractionDlq`: new Queue("extraction-dlq") with `{ connection }` (for dead-letter jobs, per D-05)
    - Export `extractionWorker`: new Worker("extraction", async (job) => await processExtractionJob(job.data), { connection, concurrency: 1 }) (per D-03)
    - Attach worker event handlers:
      - `worker.on("failed", ...)`: when `job.attemptsMade >= (job.opts.attempts || 1)`, add failed job to extractionDlq with `{ originalJobId, data, error: { message, stacktrace } }` (per D-05)
      - `worker.on("error", ...)`: log error (Pitfall 4 — missing error listener causes unhandled exceptions)

    ### 3. src/services/extraction.ts
    Create the extraction worker processor. Follow the pattern from PATTERNS.md §service pattern (conversation.ts analog). Do NOT re-read conversation.ts — use the patterns already extracted.

    - Module-level imports: `OpenAI` (singleton), `zodResponseFormat` from "openai/helpers/zod", `fs`/`path`/`fileURLToPath` for prompt loading, `env` from config, `createItem` from fsrs.ts, `prisma` from lib/prisma.ts, and schemas/types from types/extraction.ts
    - Module-level OpenAI client: `const openai = new OpenAI()` — created once, reused per job (anti-pattern avoidance from RESEARCH.md)
    - Module-level system prompt: loaded via `fs.readFileSync` at module init (same pattern as conversation.ts)
    - Export function `processExtractionJob(data: ExtractionJobPayload): Promise<void>`:
      1. Replace `{{targetLanguage}}` and `{{nativeLanguage}}` placeholders in system prompt (D-10)
      2. Build user message: include `recentContext` if present, append the `messageContent`
      3. Call `openai.chat.completions.parse()` with:
         - `model: env.EXTRACTION_MODEL` ("gpt-4o-mini" per D-01)
         - `messages: [{ role: "system", content: systemPrompt }, { role: "user", content: userMessage }]`
         - `response_format: zodResponseFormat(ExtractionResultSchema, "extraction")` (per D-06/D-07)
         - `temperature: 0.1` (deterministic extraction)
         - `max_tokens: 300` (small output — RESEARCH Pitfall 2 mitigation)
         - Second-arg timeout: `{ timeout: 15_000 }` (15s LLM timeout — RESEARCH Pitfall 2)
      4. Check `parsed` result:
         - If `null` (refusal): log warning with refusal reason, return gracefully
         - If valid: proceed to persistence
      5. For each item in `parsed.detectedItems`:
         - **Dedup check**: `prisma.reviewItem.findFirst({ where: { userId: data.userId, source: item.source, type: item.type } })`
         - If item exists: log "Skipping duplicate item" and continue (per RESEARCH recommendation)
         - If new: `createItem({ userId: data.userId, source: item.source, type: item.type, language: data.targetLanguage })`
         - If `createItem` throws: log error and continue to next item (partial success, anti-pattern from RESEARCH)
      6. Log `typosIgnored` array for observability

    ### 4. src/events/messageCreate.ts (MODIFY)
    Extend the existing messageCreate handler to enqueue extraction jobs after the conversation response completes (D-02):

    - Add imports: `extractionQueue` from "../lib/queue.js", `prisma` from "../lib/prisma.js"
    - Inside the try block, AFTER `await handleConversationMessage(...)`, call `await enqueueExtraction(session, message)`
    - Create `async function enqueueExtraction(session, message: Message)`:
      1. Fetch user from DB: `prisma.user.findUnique({ where: { discordId: session.userId } })`
      2. If no user found, return silently (no extraction possible without language config)
      3. Fetch last 2-3 messages for context: `prisma.message.findMany({ where: { sessionId: session.id }, orderBy: { createdAt: "desc" }, take: 3, select: { role: true, content: true } })`
      4. Build `recentContext` string: reverse the messages, join as "role: content\n..." (D-04)
      5. Call `extractionQueue.add("extract", { userId: user.id, sessionId: session.id, messageContent: message.content, targetLanguage: user.targetLanguage, nativeLanguage: user.nativeLanguage, recentContext }, { attempts: 3, backoff: { type: "exponential", delay: 1000 } })`
      6. Wrap enqueue in try/catch — if Redis is down, log the error but do NOT fail the conversation reply (anti-pattern from RESEARCH: "If BullMQ enqueue fails, catch and log — do not fail the user's reply")

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-01 | Tampering | messageCreate.ts — job injection via message content | medium | mitigate | Job payload is constructed server-side from authenticated session data (userId from Discord auth). `messageContent` is user-provided but processed through Prisma `create()` with parameterised queries — never executed as code. Zod schema (ExtractionJobPayloadSchema) validates payload before processing. |
| T-04-02 | Information Disclosure | Redis connection — REDIS_URL exposure | low | mitigate | REDIS_URL is stored in .env (not in git), passed via environment variable. Docker Compose exposes Redis on internal network only (not published to host). ioredis connection uses encrypted Redis if TLS-configured URL is provided. |
| T-04-03 | Spoofing | extraction.ts — LLM prompt injection via crafted messages | high | mitigate | Extraction system prompt is a static file on disk. User message content is injected at a single specific location in the user message, not as system-level instructions. OpenAI's structured output (`zodResponseFormat` with constrained decoding via FSM token masking) limits output to the Zod schema — even if injection attempts alter behavior, the output must conform to `{ detectedItems, typosIgnored }`. Temperature 0.1 reduces variability. |
| T-04-04 | Tampering | extract.ts — duplicate job processing | low | accept | BullMQ's at-least-once delivery may reprocess a job on worker crash. Dedup check (`findFirst` before `createItem`) prevents exact duplicates. In the rare case of a race condition (two concurrent checks both find no item), the worst outcome is one duplicate ReviewItem — low severity, acceptable for v1. |
| T-04-05 | Information Disclosure | extraction.ts — OpenAI API key exposure | medium | mitigate | API key passed via `OPENAI_API_KEY` env var (already configured). The OpenAI SDK reads from `process.env.OPENAI_API_KEY` automatically. Key never logged or exposed in job payloads. |
| T-04-SC | Tampering | npm install — bullmq, ioredis | high | mitigate | Both packages are from well-established registries. bullmq (taskforcesh, 7.3M/week, 10yr history) and ioredis (luin, 24M/week, 10yr history). See RESEARCH.md Package Legitimacy Audit. Insert `checkpoint:human-verify` before npm install to allow user inspection. **UPDATE:** The orchestrator handles npm install autonomously in the execution plan. The `npm install bullmq ioredis` command is part of Task 1's action. If the executor is autonomous, this runs without a checkpoint. The RESEARCH.md flagged bullmq as [SUS] due to the latest patch being 2 days old, but this is a false positive per the research analysis. No blocking checkpoint needed — the threat is noted for awareness. |
</threat_model>
