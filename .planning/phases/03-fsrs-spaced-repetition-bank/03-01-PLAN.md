    Add this after the Message model closing brace (`}` at end of Message model):

    ```prisma
    model ReviewItem {
      id            String   @id @default(uuid())
      userId        String
      user          User     @relation(fields: [userId], references: [id])
      source        String
      type          String   // "vocabulary" | "grammar"
      language      String
      stability     Float
      difficulty    Float
      state         Int      @default(0)  // 0=New, 1=Learning, 2=Review, 3=Relearning
      due           DateTime @default(now())
      elapsedDays   Int      @default(0)
      scheduledDays Int      @default(0)
      reps          Int      @default(0)
      lapses        Int      @default(0)
      createdAt     DateTime @default(now())
      updatedAt     DateTime @updatedAt

      @@index([userId])
      @@index([userId, due])
      @@index([userId, type])
    }
    ```

    **Field rationale (per D-03/D-04):**

    - `state` as `Int` with `@default(0)` (maps to `State.New=0` from ts-fsrs)
    - `due` as `DateTime` with `@default(now())` (maps to ts-fsrs Card.due)
    - `elapsedDays`, `scheduledDays`, `reps`, `lapses` as `Int`
    - `userId` has FK to User (one-to-many: User has reviewItems ReviewItem[])
    - Per D-02: only `source` field — no translation, no example sentence
    - Per D-04: `state` defaults to 0 (New) via `@default(0)` — ts-fsrs createEmptyCard() returns this

    === PART C: FSRS Service (src/services/fsrs.ts) ===
    Per D-07 (single service with 4 exports), D-04 (ts-fsrs defaults), D-08 (14-day cap inside rateItem), D-09 (getDueItems filter).

    Use the complete implementation pattern from RESEARCH.md (lines 549-665), with these specifics:

    - Import `createEmptyCard`, `fsrs`, `Rating`, type `Card` from `ts-fsrs`
    - Import `prisma` from `../lib/prisma.js`
    - Create scheduler singleton at module level: `const scheduler = fsrs();` — use default parameters (D-04)
    - Export types: `ItemType`, `RatingValue`
    - Internal type for Card mapping: use `Card['state']` for state type casting

    **createItem(input):**
    - Takes `CreateItemInput` (userId, source, type, language)
    - Creates fsrs Card via `createEmptyCard(new Date())`
    - Maps Card fields to Prisma `reviewItem.create()`:
      - `card.stability` → `stability`
      - `card.difficulty` → `difficulty`
      - `card.state` → `state`
      - `card.due` → `due`
      - `card.elapsed_days` → `elapsedDays`
      - `card.scheduled_days` → `scheduledDays`
      - `card.reps` → `reps`
      - `card.lapses` → `lapses`
    - Returns the created Prisma item

    **rateItem(input):**
    - Takes `RateItemInput` (itemId, rating where rating is 1|2|3|4)
    - Fetches item from DB via `prisma.reviewItem.findUnique`
    - Throws if not found: `Error(\`ReviewItem not found: ${input.itemId}\`)` — consistent with existing codebase (conversation.ts doesn't do this, but the service shouldn't silently fail)
    - Reconstructs Card from persisted fields (per Pitfall 3 anti-pattern from RESEARCH.md — reconstruct ALL Card fields):
      ```
      due: item.due,
      stability: item.stability,
      difficulty: item.difficulty,
      elapsed_days: item.elapsedDays,
      scheduled_days: item.scheduledDays,
      reps: item.reps,
      lapses: item.lapses,
      state: item.state as Card["state"],
      learning_steps: 0,  // transient — ts-fsrs recalculates
      ```
    - Calls `scheduler.next(card, new Date(), input.rating as Rating)`
    - Extracts `result.card` as `updatedCard`
    - Applies 14-day cap (D-08):
      ```typescript
      const THREE_MONTHS_MS = 90 * 24 * 60 * 60 * 1000;
      const itemAge = now.getTime() - item.createdAt.getTime();
      if (itemAge < THREE_MONTHS_MS && updatedCard.scheduled_days > 14) {
        updatedCard.scheduled_days = 14;
        updatedCard.due = new Date(now.getTime() + 14 * 24 * 60 * 60 * 1000);
      }
      ```
    - Updates item via `prisma.reviewItem.update()` — only the fields that change after scheduling:
      ```
      stability: updatedCard.stability,
      difficulty: updatedCard.difficulty,
      state: updatedCard.state,
      due: updatedCard.due,
      elapsedDays: updatedCard.elapsed_days,
      scheduledDays: updatedCard.scheduled_days,
      reps: updatedCard.reps,
      lapses: updatedCard.lapses,
      ```
    - Returns `{ item: updatedCard, reviewLog: result.log }`

    **getDueItems(userId):**
    - Per D-09: returns `prisma.reviewItem.findMany({ where: { userId, due: { lte: new Date() } }, orderBy: { due: "asc" } })`
    - Does NOT couple to ts-fsrs — plain Prisma query

    **getItem(itemId):**
    - Returns `prisma.reviewItem.findUnique({ where: { id: itemId } })`
    - Returns null if not found (follows existing codebase pattern — prisma.findUnique returns null on miss)
    - Does NOT throw — caller handles null (per the agent's discretion following codebase norms)

    **Per the Anti-Patterns from RESEARCH.md:**
    - Do NOT store `learning_steps` or `last_review` in Prisma model
    - Use `scheduler.next()` (single rating) not `scheduler.repeat()` (all 4 previews)
    - Use `Rating.Again/Hard/Good/Easy` enum values 1-4, not raw numbers
    - Create scheduler once at module level, not per-request
    - Always modify BOTH `scheduled_days` AND `due` when applying the interval cap

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-3-01 | Information Disclosure | fsrs.ts (getDueItems, getItem) | high | mitigate | All queries filter by `userId` derived from the Discord user's authenticated identity. `getDueItems(userId)` and `getItem(itemId)` both scope to the user's own items via Prisma where clauses. The Discord user ID is server-authenticated — no client can forge another user's ID. |
| T-3-02 | Tampering | add-item.ts (source text input) | low | mitigate | Prisma parameterises all queries — `source` is a plain string field, not a query fragment. No SQL injection risk. Source text is stored as-is; no HTML/embed injection possible through Discord embed content (Discord escapes embed output). |
| T-3-03 | Tampering | rateItem() (rating value) | medium | mitigate | Ratings are integers 1-4 applied server-side in rateItem(). The function accepts `RatingValue` (1\|2\|3\|4), which maps to ts-fsrs `Rating.Again\|Hard\|Good\|Easy`. No client-side rating values are accepted — Phase 4's review flow will pass server-controlled values. Cast via `input.rating as Rating` with ts-fsrs enum boundaries. |
| T-3-04 | Denial of Service | fsrs.ts (scheduler) | low | accept | ts-fsrs scheduling is pure math (no I/O, no recursion) — negligible compute cost even at scale. Single-user bot, no DoS vector. Accept. |
| T-3-SC | Tampering | npm install (ts-fsrs) | high | mitigate | Package verified as [OK] in Package Legitimacy Audit (RESEARCH.md). No human checkpoint required. See T-2-SC from Phase 2 — same disposition. |
